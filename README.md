## 1. Ажлын зорилго

Энэхүү лабораторийн ажлын зорилго нь Grafana k6 хэрэгслийг ашиглан веб системд ачааллын тест хийх, системийн хариу өгөх хугацаа болон хүсэлтийн гүйцэтгэлийг хэмжихэд оршино.

Туршилтад k6-ийн зөвшөөрөгдсөн дадлагын `https://test.k6.io` сайтыг ашигласан. Дараах үзүүлэлтүүдийг хэмжиж харьцуулсан:

- Хүсэлтийн хариу өгөх хугацаа (Response time)
- Дундаж хариу өгөх хугацаа (Average)
- 90 болон 95 хувийн перцентиль (p90, p95)
- Секундэд боловсруулах хүсэлтийн тоо (Throughput)
- Амжилтгүй хүсэлтийн хувь (Error rate)
- Тестийн шалгалтын амжилтын хувь (Checks)

Ашигласан команд:

```bash

```

Харин p95 үзүүлэлт хэрэглэгчийн тоо нэмэгдэх тусам өсөөгүй, харин бага зэрэг буурсан. Энэ нь туршилтын хугацаа, серверийн тухайн үеийн ачаалал болон сүлжээний хэлбэлзэл зэрэг хүчин зүйлс үр дүнд нөлөөлж болохыг харуулж байна.

## 4. SLO болон Threshold тест

### 4.1 SLO босго тооцоолол

SLO (Service Level Objective) нь системийн гүйцэтгэлд тавьж буй зорилтот шаардлага юм.

Энэ лабораторийн ажлаар baseline туршилтын p95 утгыг ашиглан SLO босгыг тооцсон.

```text
Baseline p95 = 437.39 ms

SLO = Baseline p95 × 1.5

SLO = 437.39 × 1.5

SLO = 656.085 ms
```

Ингэснээр p95 хариу өгөх хугацааны босгыг **657 ms** гэж тогтоосон.

`threshold.js` файлд дараах босгуудыг тохируулсан:

```javascript
thresholds: {
    http_req_duration: [`p(95)<${p95Limit}`],
    http_req_failed: ['rate<0.01'],
},
```

Энд:
- `http_req_duration`: HTTP хүсэлтийн p95 хариу өгөх хугацааг шалгана.
- `http_req_failed`: Амжилтгүй хүсэлтийн хувийг 1%-иас бага байлгахыг шаарддаг.

### 4.2 Threshold PASS тест

SLO босгыг 657 ms байхаар тохируулж тестийг ажиллуулсан.

Ашигласан команд:

```bash
SLO_P95=657 k6 run scripts/threshold.js
```

Үр дүн:

| Үзүүлэлт | Үр дүн |
|---|---:|
| p95 threshold | 657 ms |
| Бодит p95 | 394.88 ms |
| Error rate | 0% |
| Threshold үр дүн | PASS |

Бүтэн үр дүн: `results/threshold-pass.txt`

Бодит p95 нь 657 ms босгоос бага байсан тул threshold шалгалт амжилттай болсон.

### 4.3 Threshold FAIL тест

Threshold шалгалтын механизм зөв ажиллаж байгаа эсэхийг баталгаажуулахын тулд босгыг зориудаар 1 ms болгож багасгасан.

Ашигласан команд:

```bash

```

Үр дүн:

| Үзүүлэлт | Үр дүн |
|---|---:|
| p95 threshold | 1 ms |
| Бодит p95 | 384.03 ms |
| Error rate | 0% |
| Threshold үр дүн | FAIL |

Бүтэн үр дүн: `results/threshold-fail.txt`

Бодит p95 утга 1 ms босгоос их байсан тул k6 threshold зөрчигдсөн гэж мэдээлж тестийг амжилтгүй болгосон. Энэ нь threshold механизмыг зориудаар зөрчүүлж шалгасан туршилт юм.

## 6. Дүгнэлт

Энэхүү лабораторийн ажлаар Grafana k6 ашиглан веб системийн гүйцэтгэлийг өөр өөр ачааллын түвшинд туршиж, хариу өгөх хугацаа, throughput болон алдааны хувийг хэмжлээ.

5 VU, 30 секундийн baseline туршилтаар p95 хариу өгөх хугацаа 437.39 ms гарсан. Үүнд үндэслэн baseline p95 утгыг 1.5-аар үржүүлж 657 ms-ийн SLO босго тогтоосон.

5, 30, 100 VU-ийн харьцуулсан туршилтаар хэрэглэгчийн тоо нэмэгдэхэд throughput 7.30 req/s-ээс 142.11 req/s хүртэл өссөн. Эдгээр туршилтад HTTP хүсэлтийн алдаа гараагүй бөгөөд бүх check амжилттай болсон. Харин p95 утгууд хэрэглэгчийн тоо нэмэгдэхэд буурсан нь зөвхөн VU-ийн тоо хариу өгөх хугацааг тодорхойлдоггүй, туршилтын орчны бусад хүчин зүйлс ч нөлөөлдөг болохыг харуулж байна.

Stages туршилтаар ачааллыг 5-аас 100 VU хүртэл үе шаттай нэмэгдүүлэхээр тохируулсан боловч бодит ачаалал 60 VU хүрээд timeout болон unexpected EOF алдаа гарсан. Нийт 2515 хүсэлтийн 10 нь амжилтгүй болсон тул энэ туршилтыг бүрэн амжилттай болсон гэж үзэхгүй.

Threshold туршилтаар 657 ms босготой үед PASS, харин 1 ms босготой үед FAIL үр дүн гарсан. Ингэснээр k6-ийн threshold механизмыг ашиглан гүйцэтгэлийн шаардлага хангаж байгаа эсэхийг шалгаж, босго зөрчигдсөн тохиолдлыг илрүүлж болохыг баталгаажуулсан.

Ерөнхийдөө энэ лабораторийн ажлаар ачааллын тест зохион байгуулах, өөр өөр хэрэглэгчийн түвшинд системийн гүйцэтгэлийг харьцуулах, SLO босго тооцоолох, threshold ашиглан PASS болон FAIL нөхцөлийг шалгах дадлага эзэмшсэн.
